# 五人分工：先把工程跑起来，再改体验

每项任务一名负责人、一条codex/分支、一个PR。以下是建议排期，不代表已分派账号、创建Issue或授权改生产环境。

| 角色 | 首个任务 | 范围 | 验收 |
|---|---|---|---|
| 项目负责人（你） | 上传私有仓库、邀请、收集问题、合并PR | 排期/发布/权限审阅 | 队友都能克隆；密钥和签名不分发 |
| 队员A：记录体验 | 检查新用户记录入口、批量审核及空状态 | 相关views/CSS/record-journey | 合成测试+小屏操作，无新增确认步骤 |
| 队员B：复盘规划 | 整理真实周报与规则建议的缺口，先交小方案 | core、报告测试 | 分清事实/建议，缺记录不推断；不调用收费AI |
| 队员C：Android与数据可靠性 | 第二台电脑构建调试包、备份恢复测试 | SECOND_MACHINE流程/测试 | 独立debug包，无生产签名；记录真机未测项 |
| 队员D：好友展示与质量 | 按时间线/照片失败/撤权流程做回归 | friend-timeline及测试 | 不改RPC/RLS/授权；问题能复现，有测试证据 |

A/B/D若涉及life-app.mjs、src/views.mjs、life.css，先在Issue说明函数/样式范围，避免同时编辑同一段。代码规模小，一次合并一个模块即可，不必拆新框架。

## 建Issue时写清
- 用户遇到什么，如何复现（合成数据或经过脱敏的截图）。
- 哪几个文件/页面可以改；不能改哪些权限或数据逻辑。
- 完成后如何检验，包括失败/离线/旧数据场景。
- 谁负责实现、谁负责Review。

## 负责人合并前
- 读PR变更和测试输出，确认没有把模拟验证当成真实双机验证。
- GitHub检查通过；没有密钥、真实用户资料、模型大文件、APK。
- UI任务没有偷改云函数/SQL/正式身份；若确需修改先单独审核。
- 记录待真机验证的型号、系统和场景。构建成功不代表功能已在用户手机通过。
- 签名与发布只由负责人操作。上线后再决定下一批任务，暂不全面实施语音/商业化/复杂AI。
